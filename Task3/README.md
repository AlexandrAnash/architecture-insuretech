# Задание 3. Переход на событийную архитектуру

## 1. Проблемы и риски текущей архитектуры

- **Задержка обновления каталога.** Если агрегатор ждет ответы всех страховщиков, задержка у одного партнера может затормозить обновление локальных копий каталога в `core-app` и `ins-comp-settlement`. Число внешних зависимостей при каждом обновлении вырастет с пяти до десяти.
- **Устаревшие тарифы.** Если обновление завершится ошибкой, в локальной копии останутся данные с последнего успешного запроса. За это время страховщик мог изменить тариф.
- **Задержка формирования реестра.** С ростом продаж ночной запрос за всеми полисами за день может стать тяжелее и завершиться по тайм-ауту. Если `ins-comp-settlement` не получит данные вовремя, формирование реестра может задержаться.

## 2. Потоки событий

- **Тариф обновлен.** `ins-product-aggregator` получает данные от страховщиков через их API. Изменения по каждому страховщику публикует в Kafka по мере получения данных. `core-app` и `ins-comp-settlement` получают каждое событие и обновляют свои локальные каталоги.
- **Полис оформлен.** `core-app` публикует событие при оформлении полиса. `ins-comp-settlement` сохраняет данные о полисах в течение дня и ночью формирует реестр из своей базы.

## 3. Transactional Outbox

Использую Outbox в двух сервисах. `ins-product-aggregator` сохраняет изменение тарифа и запись о событии в одной транзакции. `core-app` так же сохраняет оформленный полис и запись о событии.

Фоновый процесс отправляет записи из Outbox в Kafka. При повторной доставке получатели проверяют ID события, чтобы применить его только один раз.
